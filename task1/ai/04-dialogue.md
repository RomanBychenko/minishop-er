## 1. Створення ER-моделі

Початкова вимога: task1/spec.md
Коміт специфікації: fd2cc97

Запит користувача:
Я написав spec.md для простого інтернет-магазину. Мені потрібно зробити ER-діаграму за цими вимогами. Хочу використати Mermaid, щоб діаграма відображалася на GitHub.

У магазині мають бути покупці, товари, категорії, замовлення та деталі замовлень. Додай потрібні атрибути, ідентифікатори та зв'язки між ними. Не потрібно робити SQL-базу даних, тільки ER-модель.
Відповідь ChatGPT:
Для такого магазину достатньо п'яти сутностей: CUSTOMER, CATEGORY, PRODUCT, PURCHASE_ORDER і ORDER_ITEM.

Ось приклад ER-діаграми в Mermaid:

erDiagram
    CUSTOMER ||--o{ PURCHASE_ORDER : "оформлює"
    CATEGORY ||--o{ PRODUCT : "містить"
    PURCHASE_ORDER ||--|{ ORDER_ITEM : "містить"
    PRODUCT ||--o{ ORDER_ITEM : "входить до"

    CUSTOMER {
        string customer_id PK
        string full_name
        string email
    }

    CATEGORY {
        string category_id PK
        string name
    }

    PRODUCT {
        string product_id PK
        string name
        decimal price
    }

    PURCHASE_ORDER {
        string order_id PK
        datetime created_at
        string status
    }

    ORDER_ITEM {
        string item_id PK
        int quantity
        decimal unit_price
    }

Покупець може створювати декілька замовлень, а категорія містити багато товарів. Сутність ORDER_ITEM потрібна, щоб зберігати кількість товару та його ціну в конкретному замовленні.

Цю діаграму можна вставити в README.md. GitHub автоматично відобразить її.

## 2. Уточнення специфікації

Контекст: task1/review-01.md

Запит користувача:
Я переглянув діаграму і порівняв її зі своїм spec.md. Помітив, що в мене написано про первинні та зовнішні ключі, хоча завдання стосується ER-моделі.

Також я назвав ORDER_ITEM таблицею деталей замовлення і не пояснив, чому є дві різні ціни. Допоможи уточнити специфікацію, але щоб вона залишалася простою.

Відповідь ChatGPT:
У цьому випадку краще уточнити три моменти.

У критеріях готовності вказати унікальні ідентифікатори, атрибути та кардинальності. Зовнішні ключі не потрібно робити обов'язковою вимогою концептуальної моделі.

Назвати ORDER_ITEM окремою сутністю «Позиція замовлення», оскільки вона має власні атрибути — кількість і ціну.

Пояснити, що PRODUCT.price — це поточна ціна товару, а ORDER_ITEM.unit_price — ціна на момент оформлення замовлення.

Структуру діаграми змінювати не обов'язково, оскільки вона вже відображає ці зв'язки. Достатньо уточнити специфікацію та повторно перевірити відповідність моделі вимогам.

## 3. Підготовка ADR

Запит користувача:
Мені ще потрібно зробити ADR для цього завдання. Хочу пояснити, чому використав окрему сутність ORDER_ITEM, а не просто з'єднав товари із замовленнями. Допоможи розібрати два варіанти та сформулювати рішення простими словами.

Відповідь ChatGPT:
Для ADR можна розглянути два варіанти.

Перший варіант: зробити прямий зв'язок між PRODUCT і PURCHASE_ORDER. Це зробить діаграму простішою, але в такій моделі буде незрозуміло, де зберігати кількість товару та його ціну під час оформлення замовлення.

Другий варіант: створити окрему сутність ORDER_ITEM. Вона дозволить зберігати кількість кожного товару та його ціну на момент покупки.

Для нашого інтернет-магазину другий варіант краще підходить, оскільки одне замовлення може містити декілька товарів. Крім того, якщо ціна товару в каталозі зміниться, інформація про старе замовлення залишиться правильною.

У результаті модель стає трохи більшою, але краще відображає роботу інтернет-магазину.

Результат: коміт 481c6f2.
